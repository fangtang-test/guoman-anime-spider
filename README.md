# 国漫数据采集（豆瓣 + 猫眼）

把「豆瓣的作品全量库」和「猫眼的每日票房」抓进一个 SQLite，再导出成一张能直接拖进
Tableau 的中文宽表。**非商用、控制频率、可断点续采。**

```
豆瓣 j/new_search_subjects  ─┐
豆瓣 rexxar 详情接口         ─┼→  SQLite  ─→  CSV / parquet  ─→  Tableau
猫眼 dashboard-ajax 票房榜   ─┤
猫眼 www/films 片单          ─┘
```

---

## 一、快速开始

需要 Python 3.10 以上，依赖都在 `requirements.txt`：

```bash
pip install -r requirements.txt
```

然后：

```bash
cd anime_spider

python run.py doctor      # 1. 先体检：环境 + 四个接口连通性
python run.py selftest    # 2. 离线自检（不联网），92 项
python run.py sync --tags 国产动画 --max-start 200 --limit 30   # 3. 小批量试跑
python run.py maoyan      # 4. 抓猫眼（73 部在映 + 近 5 日逐日票房，2~3 分钟）
python run.py export      # 5. 导出 CSV / parquet / Tableau 宽表
python run.py stats       # 进度、评分分布、编码分布
```

一条龙：`python run.py all`（= sync + maoyan + export）。

> **猫眼不给历史数据**（`date` 参数是摆设，实测六种取值都返回当天）。票房时间序列
> 只能靠**每天跑一次** `run.py maoyan` 攒出来。挂个计划任务即可。

## 二、数据源与它们的坑

这几个坑都是实测踩出来的，改代码前先看这一节。

### 豆瓣

| 用途 | 接口 | 说明 |
|---|---|---|
| 列表（全量枚举） | `https://movie.douban.com/j/new_search_subjects?tags=<标签>&sort=U&range=0,10&start=N` | 每页 20 条，JSON，无 Cookie |
| 详情 | `https://m.douban.com/rexxar/api/v2/movie/<id>`（带 `Referer: https://m.douban.com/movie/subject/<id>/`） | **77 个字段**，无 Cookie |
| 详情兜底 1 | `.../v2/tv/<id>` | 剧集用 |
| 详情兜底 2 | `https://movie.douban.com/j/subject_abstract?subject_id=<id>` | 轻量，只有 11 个字段 |

**坑 1：`type=movie` / `type=tv` 参数被豆瓣完全忽略。**
实测同一个标签下传 `movie`、传 `tv`、不传，返回的**是同一批 20 条**。
所以「按 type 分别枚举电影和剧集」这条路是死的 —— 会把电影抓三遍而**剧集一条都拿不到**。
真正的区分维度是**标签**：`动画`/`欧美动画` 基本只挂电影，`国产动画`/`日本动画` 深翻
之后才是番剧大本营（`start=200` 起就是镇魂街、一人之下、沧元图、斗破苍穹、星辰变、雪鹰领主）。
另外还有一类**档期标签**（`中国大陆`/`华语`/`豆瓣高分`），跟题材无关，但只有它们能
让豆瓣库覆盖当期档期、跟猫眼票房对上号 —— 见第五节。

**坑 2：`/rexxar/api/v2/movie/<id>` 一个端点通吃电影和剧集。**
剧集 ID 传 `/movie/` 也返回 200 + 77 字段，`is_tv=true`、`subtype=tv`、
`episodes_count=12` 全都对。**一条数据只需要一次请求**，不用先判断类型。
（注意这是「不被限流时」的行为 —— 豆瓣会**单独限 `/movie/`**，
见坑 4b，那时同一时刻 `/tv/{id}` 对剧集反而还是通的。）

**坑 3：豆瓣详情页的 HTML 是反爬页，抓不了。**
`https://movie.douban.com/subject/<id>/` 返回 HTTP 200，但只有 2965 字节，
正文是 `<form name="sec" action="/c">` 安全验证表单（含隐藏字段 `tok`/`cha`/`sol`）。
评分、`div#info`、`application/ld+json` 全都找不到 —— **不是选择器写错了，是页面就是验证页**。
必须走上面的 rexxar JSON 接口。

**坑 4：限流是静默的。**
连续快速打几十次之后，接口开始**返回空数据但 HTTP 仍然是 200**，
跟真的翻到底长得一模一样。当时一度误判成「接口改了」，等 90 秒后完全恢复。
更阴的是**换个标签也不会清零**：实测「中国大陆」连翻 10 页之后紧接着抓「华语」，
对方的首页和次页一起变空 —— 差点被记成「华语没数据」。

所以代码里把三种情况严格分开：

| 情况 | 返回值 | 处理 |
|---|---|---|
| 请求彻底失败（含重试） | `None` | 不推进 `start`，本轮收工，下轮接着翻 |
| 空页 | `[]` | 先当限流处理（见下），确认是空的才计数 |
| 有数据 | `list` | 正常入库 |

空页的确认过程是**递增等待**：等 `empty_recheck_wait`（默认 20 秒）重取，
还空就翻倍再等（上限 `empty_recheck_max` = 90 秒），普通位置重试
`empty_retries`（默认 2）次。连续 `empty_pages_stop`（默认 2）个位置
都确认为空才判定「翻到底」。

还有一个硬证据：**`start=0` 的首页永远不可能为空**（任何标签至少有一页）。
所以首页空了一律按限流处理，重试次数自动放宽到 5 次，
免得一个被限流的标签被静悄悄地整个跳过。

另外换标签之间会歇 `tag_cooldown`（默认 15 秒）。
`http.min_delay` 也别关（默认 1.2~2.8 秒随机）—— 实测这个速率下
连翻 10 页仍会被打嗝，靠上面的重试兜住。

这套逻辑有 5 项离线自检专门覆盖（假数据源注入空页/失败/断点场景，
见 `run.py selftest` 的「[限流恢复]」段）。

**坑 4b：详情接口的限流走 HTTP 400，不是 429 —— 这个坑最贵。**

详情接口被限流时返回的是：

```
HTTP 400  218B
{"request": "GET /v2/movie/1292052", "msg": "subject_ip_rate_limit",
 "code": 1309, "localized_message": "您所在的网络存在异常，请登录后重试。"}
```

早期版本只看状态码，把 400 当成「这个端点不可用」，于是**静默降级**到轻量的
`subject_abstract`（20 个字段 vs 77 个）。后果是 **390 条详情里有 161 条
（全是电影）没有简介/语言/时长/原名**，而且因为这些行已经写进
`douban_detail` 了，「只补没抓过的」永远看不见它们 —— **错误永久留在库里**。

现在的处理：

- 认 `code 1309`（或 `msg` 里含 `rate_limit`），按限流处理而不是按端点故障
- 每个 kind 递增等待重试（0s → 45s → 90s）
- **`/movie/` 被限流不等于没戏**：实测同一时刻 `/tv/{id}` 对剧集仍是 200，
  所以两个 kind 都给机会，都还在限流才抛 `RateLimited`
- 抛出来之后 `sync_details` **直接中止本轮**，不写降级行，并打印提示；
  已抓到的照常入库，剩下的下次重跑接着抓
- `pending_detail_ids` 会把已经带 `_degraded` 标记的行**重新排队**，
  而且**排在「完全没抓过」的行前面** —— 降级行是已经躺在库里的错数据，
  会直接进宽表；没抓过的行只是缺，不污染已有结果。所以先修坏的。历史脏数据能自愈
- `run.py doctor` 遇到限流时打印 `[限流] 豆瓣详情接口 …` 并正常退出（**不是**
  `[失败]`，也不抛异常）—— 它测的是采集真正走的路径，所以限流也会被如实报出来

限流时长实测约几分钟到几十分钟（抓取时最长的一次等了约 20 分钟恢复）。
这一段有 12 项离线自检
（见 `run.py selftest` 的「[豆瓣限流]」段），用假客户端把等待压到 0 秒。

### 猫眼

| 用途 | 地址 | 说明 |
|---|---|---|
| **真票房榜** | `https://piaofang.maoyan.com/dashboard-ajax/movie` | 免签名、免登录、免浏览器、**无字体混淆**，不传参数就有 73 部在映 + 当日大盘 |
| 单片详情 | 同上 `?movieId=<id>` | `category`（类型）+ `boxTrends[]`（近 5 日逐日票房） |
| 片单 | `https://www.maoyan.com/films?showType=1`（正在热映）/ `showType=2`（即将上映·预售） | HTML，含上映日期/主演/类型 |
| 单片页 | `https://www.maoyan.com/films/<id>` | **废**：纯 JS 骨架，见下 |

**坑 5：`showType` 的含义容易搞反。**
`1` = **正在热映**，`2` = **即将上映/预售**，`3`/`4` = 空页。
（早期版本只抓了 `showType=2`，等于只拿到预售片单，把「正在热映」整块漏掉。）

**坑 6：猫眼单片页 HTML 里什么都没有。**
`/films/1578266` 返回 12377 字节，但 `<title>` 是「猫眼电影PC端」，正文里
**片名出现 0 次、票房 0 次**，数据全靠 `movie-detail-index.*.js` 渲染。
而且带字体反爬（`@font-face{font-family:"mtsi-font"}` + `.stonefont`）：
数字被换成 PUA 码位，得下载 woff、比对字形轮廓指纹才能还原。
**这条路已经整体废弃** —— 票房榜接口直接给真数字，没必要跟字体较劲。
`animedata/stonefont.py` 还留着，但主流程不引用它（只有想抠「预售票房」时才用得上，
那个数字在片单页里确实还是混淆的）。

**坑 7：片单页的 `movie-item` 节点数是实际卡片的 3 倍。**
一页 54 个 `div[contains(@class,"movie-item")]`，其中只有 **18 个**
`div.movie-item.movie-item-hover.film-channel` 是真卡片，另外 36 个是
hover 浮层 + 纯标题占位。
按 `movie-item` 抓会得到 3 倍重复行，而且**枚举序号会被当成排名**（1,4,7,10,13…）。
正确做法：**只取 `div[contains(@class,"film-channel")]`**。
（真卡片的 `data-val="{movieid:NNN}"` 挂在**内层 `<a>`** 上，外层 `div` 的是 `None`。）

**坑 8：同一个接口里两种票房单位。**
`movieList.list[].box` 单位是**分**（`5220501131` 分 = 5220.5 万元），
`boxTrends[].box` 单位是**元**（`10633807` = 1063.3 万元）。
代码里前者除以 100 存 `box_yuan`，后者直接用 —— 别搞混。

**坑 9：`boxTrends` 只给最近 5 天**，跟上映多久没关系（上映 83 天的《功夫女足》
和上映首日的片子一样都只返回 5 天）。这是滚动窗口，不是完整曲线。

### 编码（用户提的那个问题）

老页面确实不是 UTF-8，`animedata/http.py` 专门处理：

- 候选编码按 **BOM > HTTP 头 > HTML meta/XML 声明 > utf-8 > chardet > gb18030** 排序，
  逐个严格试解，取第一个成功的
- `GB2312` / `GBK` 一律归一到 **`GB18030`**（超集，能吃下生僻字）
- **专治「响应头谎报 latin-1、真实是 GBK」**：`SUSPECT_ENCODINGS` 里的编码
  （`iso-8859-1`/`latin-1`/`ascii`/`cp1252`…）**只接受纯 ASCII**，含非 ASCII 字节就跳过继续找
- `utf-8-sig` 必须原样保留（不能别名成 `utf-8`），否则 BOM 不会被剥离，文本开头留 `\ufeff`
- `looks_garbled()` 用替换字符占比 > 2% 判乱码

这些都有离线测试覆盖（`run.py selftest`），**不需要联网**就能验证 ——
因为当前豆瓣/猫眼接口返回的全是 UTF-8，联网跑根本碰不到 GBK 那条路径。

## 三、命令

| 命令 | 作用 |
|---|---|
| `doctor` | 环境 + 依赖 + 四个接口连通性体检 |
| `selftest` | **离线**自检 92 项：编码自适应 / 字段解析 / 猫眼解析 / 宽表（含跨源匹配） / 限流恢复 / 补全优先级 / 豆瓣限流 / 导出清理 |
| `verify [--samples N]` | 验证标签枚举有没有同时覆盖电影和剧集 |
| `sync [--limit N] [--skip-detail] [--skip-list] [--tags a,b] [--max-start N] [--all-details]` | 豆瓣采集 |
| `maoyan [--limit N] [--no-trends]` | 猫眼票房榜 + 大盘 + 片单 + 单片逐日票房 |
| `export` | 导出 CSV / parquet / Tableau 宽表 |
| `stats` | 数据库概览 + 编码分布 |
| `all` | 采集 + 导出 |

全局参数：`-c/--config`（默认 `config.toml`）、`-v/--verbose`、`--log-file`。

**改完代码先跑 `selftest`** —— 它已经抓出过 7 个真 bug，包括「电影集数显示成 0」
这种只有 Tableau 里才会发现的问题，和「限流被当成端点故障、详情被静默削掉」
这种只有对比字段数才会发现的问题。

采集是**幂等 + 增量的**：`douban_list` 以 `subject_id` 为主键，详情只补没抓过的
以及**被降级过的**（见坑 4b），`pending_detail_ids` 负责排队。随时 Ctrl+C，重跑接着采。

想只修数据、不重新枚举列表，用 `--skip-list`（列表层翻 9 个标签很慢，
而修详情根本不需要它）。

## 四、目录结构与产物

```
anime_spider/
├─ run.py                  入口（也是唯一需要记的命令）
├─ config.toml             所有可调项都在这里
├─ requirements.txt
├─ animedata/
│  ├─ config.py            tomllib 读配置（用标准库，不依赖 pyyaml）
│  ├─ http.py              限速 + 重试 + 编码自适应 + 乱码检测
│  ├─ db.py                SQLite schema / upsert / 迁移 / 统计
│  ├─ douban.py            列表枚举 + 详情补全
│  ├─ maoyan.py            票房榜 + 大盘 + 片单 + 逐日票房
│  ├─ stonefont.py         石头字体解码（当前主流程未使用）
│  ├─ export.py            宽表构建 + 导出
│  └─ pipeline.py          子命令、体检、离线自检
├─ data/anime.db
├─ exports/                导出产物
└─ logs/run.log
```

### 数据库表

| 表 | 主键 | 内容 |
|---|---|---|
| `douban_list` | `subject_id` | 列表层：片名/评分/导演/主演/封面/累积标签 |
| `douban_detail` | `subject_id` | 详情层：27 个扁平字段 + **`detail_json` 原始 JSON 全量存档** |
| `maoyan_board` | `snapshot_date, movie_id` | 票房榜：累计票房（分+元+文本）/票房占比/排片占比/上座率/场均人次/场次/**真排名** |
| `maoyan_box_trend` | `snapshot_date, movie_id, box_date` | 单片逐日票房（近 5 日滚动窗口） |
| `maoyan_nation` | `snapshot_date` | 当日大盘：总票房/分账/场次/观影人次 |
| `maoyan_list` | `snapshot_date, movie_id, show_type` | 片单：状态（购票/预售）/类型/主演/上映日期 |
| `crawl_state` | `key` | 断点续采用 |
| `fetch_log` | — | 每次请求的 status/编码/字节数/耗时/重试/错误 |

`detail_json` 存了原始 JSON —— 以后想加字段，不用重抓，直接从库里挖。

### 导出产物（`exports/`）

`豆瓣明细` / `Tableau_作品宽表` / `猫眼票房榜` / `猫眼逐日票房` / `猫眼大盘` /
`猫眼片单` / `字段说明` / `概览.json`，每个都是 **CSV + parquet** 两份。

- CSV 一律 `utf-8-sig`，Excel 双击不乱码
- `字段说明.csv` 是 46 行字段字典（字段/类型/说明/是否有值），可以直接当 Tableau 的数据字典
- `导出清单.json` 记录本次产出了哪些文件。**schema 改过之后（比如旧版的
  `猫眼在映时序.csv` 被四张新表取代），下次 `export` 会自动删掉上次产出、
  这次不再产出的文件** —— 免得把错列的老文件拖进 Tableau。它只删自己写过的，
  你手动放进 `exports/` 的东西不会被碰

### Tableau 宽表（46 列）

中文列名，按维度/度量分好：

- **维度**：作品ID / 作品名称 / 作品类型（电影|剧集番剧）/ **详情完整** / 年份 / 年代 / 评分档 /
  评分星级 / 热度档 / 主类型 / 类型2 / 类型3 / 类型数 / 地区 / 主出品地区 /
  是否国产 / 语言 / 时长档 / 导演 / 主演 / 别名 / 简介 / 封面图 / 豆瓣链接
- **度量**：评分 / 评分人数 / 时长分钟 / 集数 / 短评数 / 影评数 / 猫眼累计票房 /
  猫眼场次 / 猫眼当日排名 …
- **猫眼列**（10 个）：猫眼快照日期 / 累计票房 / 票房占比 / 排片占比 / 上座率 /
  场均人次 / 场次 / 当日排名 / 上映状态 / 类型

> **先筛 `详情完整 = "是"` 再分析。** `详情完整 = "否"` 的行是豆瓣详情被限流降级的结果
> （见坑 4b），它们的简介/原名/语言/时长是空的 —— 在 Tableau 里这和「这部片确实没简介」
> 长得一模一样。`概览.json` 的 `详情完整度` 会报出这个数量，`run.py sync --skip-list`
> 会自动优先修这些行。

几个刻意的处理：

- **`集数` 电影为空**（不是 0）。豆瓣对电影返回 `episodes_count=0`，
  少数栏目剧集也返回 0 —— 两种 0 都没意义，一律置空，
  否则 Tableau 算平均/计数会把 0 当真实值算进去
- **`是否国产` 是宽口径**：`countries` 里只要含「中国大陆」就算「是」，
  所以合拍片（《中华小子》法国/中国大陆）也算。想看纯国产用 **`主出品地区`** 过滤
- **猫眼并表按片名匹配，分三档优先，后两档都带唯一性检查**（猫眼不提供它自己的
  `movieId` ↔ 豆瓣 `subject_id` 对照表）：
  1. **完全相等**（归一化：去空格与标点、转小写）
  2. **豆瓣别名** —— 拿 `aka`（港台译名/原名）去撞猫眼片名
  3. **去副标题后的主体名** —— 《复联4：终局之战》↔《复联4：终局之战（加码臻享版）》。
     这一档是**弱键**，要求**两边都确实去掉了副标题**、且该主体名在两边都只对应
     一部片，否则不挂（不然《小猪佩奇》会认领《小猪佩奇·完美假期》的票房，
     或者一部片的票房被复制到多行上、求和直接翻倍）
- **匹配不上就留空**，「把 A 片的票房挂到 B 片上」比留空有害得多。
  所以 `概览.json` 里有 `猫眼匹配.匹配率`；匹配率低通常是数据本身不重叠（详见下）

## 五、关于匹配率：两个原因，两个办法

宽表里那 10 个猫眼列全靠**片名**连接（猫眼不给它自己的 `movieId` ↔ 豆瓣
`subject_id` 对照表）。所以匹配率取决于两件事：

### 原因 1：豆瓣库里根本没有这部片 → 用「档期标签」

第一次跑完是 **0%**，补了 `动画` 标签后 **1.4%**（只有《机器人总动员》对上 ——
它正在重映，所以猫眼有票房）。原因是当时豆瓣库里 40 条全是《中华小子》
《虹猫蓝兔七侠传》这类**老国漫**，而猫眼票房榜是**当下在映**的片子，
两边片名根本不重叠。

**题材标签（`动画`/`国产动画`）捞不到当期档期** —— 它们按评分排序，出来的都是经典。
实测：`tags=动画` 首页是千与千寻、疯狂动物城；`tags=热门`/`tags=最新` 在这个接口上
**返回 0 条**（那是另一个接口的标签表，不能混用）。

**真正管用的是「档期标签」**：

| 标签 | 首页 20 条里精确命中猫眼在映榜 |
|---|---|
| `中国大陆` | **7 条**（欢迎来龙餐馆 / 八仙！/ 敦煌英雄 / 抓特务 / 空枪 / 老江湖 / 年会不能停！2）|
| `华语` | 4 条（年会不能停！2 / 欢迎来龙餐馆 / 抓特务 / 八仙！）|
| `豆瓣高分` | 2 条（肖申克的救赎 / 机器人总动员）|
| `动画` / `国产动画` / `日本动画` | 0 条 |

所以默认标签里已经加了 `中国大陆`、`华语`、`豆瓣高分`。

### 原因 2：片子进了列表层，却没进详情层 → 用「优先补详情」

**宽表只由详情层构建**，列表层捞到但没抓详情的条目在宽表里根本不存在。
而 `--limit` 是按顺序截断的 —— 原来的顺序是「评分从高到低」，
**正在上映的新片往往还没出分（或分很低），一排就排到最后**。

实测数据（556 条列表 / 330 条详情时）：

| | 数量 |
|---|---|
| 猫眼在映榜片名出现在豆瓣**列表层** | **17 / 73** |
| 猫眼在映榜片名出现在豆瓣**详情层** | **4 / 73** |
| 最终宽表匹配上 | 3 / 330（0.9%）|

17 掉到 4，丢的就是 `--limit` 那一刀。

**已修**：`db.pending_detail_ids` 现在先补「片名精确出现在猫眼票房榜上」的条目，
然后才按评分排；并且 `sync` 里把猫眼快照挪到了补详情**之前**，
这样第一次跑就能用上这个优先级（详见 `douban.py` / `db.py` 里的注释）。

修完再补 60 条详情（详情层 330 → 390）：

| | 修复前 | 修复后 |
|---|---|---|
| 猫眼在映榜片名在**列表层** | 17 / 73 | 17 / 73 |
| 猫眼在映榜片名在**详情层** | 4 / 73 | **17 / 73** |
| 宽表匹配上 | 3 / 330（0.9%）| **16 / 390（4.1%）** |

**16 不是 17，是设计如此**：唯一没挂上的是《浪浪山小妖怪：幻境奇旅》
（猫眼带副标题），而豆瓣那条标题是《浪浪山小妖怪》（无副标题）——
弱键那一档要求两边都确实去掉过副标题，所以拒绝挂。这比把 A 片票房挂到 B 片上安全。

注意 **4.1% 这个分母是「宽表 390 行」**，而宽表是**国漫库**（大半是老片），
猫眼榜是**当期在映**。真正有意义的是「有重叠的那部分挂上了多少」：**16 / 17 = 94%**。
所以匹配率低不代表程序不对，先看重叠有多少 —— `_diag_join.py` 那个诊断就是干这个的
（工具脚本，不是程序的一部分，已随收尾清理删除，需要时照本文思路重写几行即可）。

所以**不要用 `--limit` 卡在几百**，要匹配率就让它把详情补完 ——
详情是增量的，跑过的不再重复抓，断了重跑即可。

```powershell
python run.py sync        # 全量：先枚举，再抓猫眼票房榜，再按优先级补详情
python run.py export
```

想整体做扎实就全量跑一遍（9 个标签翻到 `start=8000`，耗时较长，
可以分批/挂夜里；`list_start:<标签>` 断点会记住翻到哪儿了）。

## 六、合规

- 个人学习与研究用途，**非商用**
- `http.min_delay` 默认 1.2~2.8 秒随机，**别调小**；豆瓣限流是静默的，
  调小只会让你拿到一堆假空页，反而更慢
- 详情抓取约 0.5 条/秒，跑 5000 条约 3 小时 —— 分批跑，或者挂夜里
- 猫眼每天一次就够（榜单 5 秒刷一次，但你要的是「每日快照」这个粒度）
- 不存用户数据、不绕验证码、不破付费墙；豆瓣验证页出现时程序会当失败处理，不会硬闯

## 七、改代码时的注意事项

1. **`selftest` 是唯一的安全网。** 没有网络也能跑，92 项覆盖所有解析分支
   （包括「片单 3 倍重复节点」「主体名弱键不得错配」「限流空页递增重试」
   「导出时删过期产物」这类已经踩过的坑）。
   加了新解析就加一条 `check(...)`。
2. **豆瓣的 `type` 参数永远不要再用。** 见坑 1。要区分电影/剧集只看 `is_tv`。
3. **不要让 `None`（请求失败）和 `[]`（真空页）走同一条路。** 见坑 4。
   空页要走 `_fetch_page_recovering` 的递增重试，别信第一次的结果。
4. **猫眼片单只认 `film-channel`。** 见坑 7。
5. **猫眼两种票房单位。** 见坑 8。
6. Windows 控制台跑带中文列名的 `python -c "..."` 会被 GBK 码页弄坏
   （报 `KeyError: "None of [Index(['��������'...])]"`）——
   含中文的片段写成临时 `.py` 文件跑，或者先 `chcp 65001`。
